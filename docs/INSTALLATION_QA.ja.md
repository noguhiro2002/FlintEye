<a id="what-the-browser-checks"></a>
## ブラウザによるチェック内容

`frontend/tests/installed.mjs` は、API応答を置換することなく、インストールされたアプリケーションのHTTPサーバーに接続します。ブラウザ経由で管理者を作成し、組み込まれたリリース情報/コミットを確認し、2台の合成RTSPカメラを登録して設定を保存します。その後、ダッシュボード、情報、設定、ライブビュー、マルチビュー、録画画面を開き、WebRTC映像の進行と音声の受信をチェックします。また、実際の録画データの再生/ダウンロードと、閲覧者のログインおよび書き込み拒否の検証を行います。

音声は両方のカメラでオフの状態で開始されます。テストは1台のカメラを有効にし、標準録画音声（16-bit PCM、16 kHz、モノラル）を検証します。2台目のカメラは無音のままである必要があります。FFmpegは生成されたすべての録画を最後まで読み込み、デコードエラーがあれば失敗とみなします。物理的なカメラ、マイク、実際のパスワード、個人の映像は必要ありません。

**監視停止 (Stop monitoring)** は、APIを有効にしたままメディアプロセスを停止させる必要があります。設定の保存によってプロセスが再起動されてはなりません。通常の終了 (Quit) 要求では、削除前にAPIおよび所有しているメディアリスナーを閉じる必要があります。アンインストールでは、アカウント、設定、録画データを保持したままプログラムを削除しなければなりません。再インストールでは、管理者パスワードを再利用し、両方のカメラ、音声設定、録画インベントリを維持する必要があります。失敗後のクリーンアップによって通常の終了テストが合格状態になることはありません。

既存の合成フロントエンドテストは、これらの実際のバックエンドテストと並行して、エラー、応答速度、レスポンシブレイアウト、アクセシビリティをカバーしています。

映像を配信する仮想カメラは、アプリケーションのインストール先とは別の場所に隔離されたメディアツールのコピーを使用します。テスト実行中は、インストール済みの実行ファイルを開いたままにしたり、アンインストーラーがテスト用のカメラをアプリケーションプロセスとして誤認したりしないようにしてください。

<a id="build-time-matrix"></a>
## ビルド時のマトリックス

各ケースはビルドのソースコミットを使用します。インストーラーのケースでは既存のアーティファクトを再利用するため、手法ごとにアプリケーションを再コンパイルすることはありません。

| ホスト / ターゲット | CPU | インストール方法 |
| --- | --- | --- |
| Windows Server 2022 / Windows 11 ARM | x64 / ARM64 | EXE; ワンスクリプトインストーラー |
| macOS 15 および 26 | Intel / Apple Silicon | DMG; ワンスクリプトインストーラー |
| Ubuntu 24.04 desktop (使い捨てXvfbコンテナ内) | x64 / ARM64 | DEB; ワンスクリプトインストーラー; 実際のデスクトップエントリー |
| Rocky Linux 9 desktop (使い捨てXvfbコンテナ内) | x64 / ARM64 | RPM; ワンスクリプトインストーラー; 実際のデスクトップエントリー |
| Ubuntu 24.04 ホストVM | x64 / ARM64 | システム同梱のsystemdユニットと個別のQAサービス/状態ディレクトリ |
| Linux Docker Engine | x64 / ARM64 | Distribution Compose; ビルド済みイメージを使用した開発用Compose |
| Windows, macOS 15, Ubuntu 24.04 | x64 / ARM64 | 専用Python環境でのソーススナップショット |

**32の必須ケース**があります。macOSランナーは `latest` ではなく 15/26 および Intel/Apple Silicon に固定されています。[GitHubのランナーリファレンス](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)を参照してください。Windows Server CIはWindows 10の互換性を確立しません。Linuxコンテナは物理的なLinuxデスクトップではなく、Docker EngineはDocker Desktopではありません。

WindowsスクリプトのQAでは、サポートされている`-Silent -NoStart`オプションを使用し、その後インストール済みの実行ファイルを開始します。インターネット由来のメタデータは保持されます。対話型シェルの警告、SmartScreen、およびOS標準の許可ダイアログは、実機での確認項目となります。macOSスクリプトのQAでは、通常の `open` による起動要求を非同期で監視し、OSの承認ダイアログによって診断情報の収集が妨げられないようにします。

<a id="macos-installation-integrity-and-permission-are-separate"></a>
## macOSのインストール、整合性、および権限について

DMGおよびワンスクリプトの両インストール方法において、宣言された実行ファイル、有効な内部リンク、FlintEyeアイコン、および有効なアドホック整合性署名が生成される必要があります。その後、テストは `open FlintEye.app` を使用してLaunch Servicesを呼び出し、通常のダウンロード検疫を維持します。ヘッドレスサブプロセスや `codesign --verify` の成功単体では、通常の初回起動とはみなされません。

コミュニティプレビュー版にはDeveloper IDや公証がありません。macOSがアドホックな初回起動を明示的に拒否した場合、検証結果には `os_launch: manual-required` と記録され、API/GUI/終了/再インストールは `not-run` となりますが、削除チェックは行われます。これは**アプリケーションテスト合格ではありません**。この制限事項が開示された「開発中 (UNDER DEVELOPMENT)」プレビューに伴う場合があります。実行ファイルの欠落、破損した署名、認識されない起動失敗、または実行されたテストの失敗は、配布ファイルの集約を阻止します。このスイートは検疫の解除、Gatekeeperの無効化、または承認のシミュレーションを行うことはありません。

macOSで内部的なXProtectエラーが報告された場合、QAは同一ランナー上で、新たにコンパイルした「別の無害な検証用アプリ」を評価します。内部エラーのテキストは、アプリ名を置き換えた後に完全に一致しなければなりません。アプリ固有の追加の指摘事項や脅威判定が出た場合は、配布判定は不合格となります。この比較は、実行権限の付与やFlintEyeの動作を証明するものではありません。初回起動が拒否されたことが確認された場合でも、API/GUIテストは未実行のままとなります。

実際のMacでは、FlintEyeを開こうとした後、提示された場合は **システム設定 → プライバシーとセキュリティ → このまま開く (Open Anyway) → 開く (Open)** を使用してください。管理されたMacでは管理者の支援が必要な場合があります。初回起動を記録し、承認後にAPI/GUI/削除チェックを繰り返してください。`amfid` による拒否は、実行ファイルが存在していても「ファイルが見つかりません」というエラーを引き起こす可能性があります。これに対処するためにアカウントや設定を消去しないでください。[インストールとOS確認](INSTALL.ja.md#unsigned-packages)を参照してください。

<a id="evidence-and-publication"></a>
## 証拠と公開

**Actions → Build release → Artifacts** を開いてください。各 `lifecycle-*` アーティファクトには `lifecycle.json`、ブラウザのスクリーンショット/ビデオ、Playwrightトレース、実際のAPI/ビルド情報、録画デコード/音声チェック、フィクスチャログ、および利用可能なアプリ/OSログが含まれています。ジョブが失敗した場合でも失敗の証拠はアップロードされます。すべての認証情報とメディアは合成されたものです。個人用プロファイルで自動テストの実行環境を再利用しないでください。

配布ファイルの集約には、完全なマトリックスと、コミット/リリースが一致する証拠が必要です。ケースの欠落、ステージの失敗、改ざんされたアーティファクト、または実際のブラウザでの証拠の欠落は `release-bundle` を阻止します。添付された `QA-RESULTS.json` は、CI完了ケースと、macOSの承認要件や保留中の物理環境での受け入れテストを区別します。既存のリリースやファイルは上書きされません。

`Diagnose existing installers`は、検証ツールやインストーラースクリプトを修正する間、アーカイブ済みのEXE/DMGファイルを再利用します。これは、コンパイル対象のアプリケーションとネイティブビルドの入力内容に変更がないことを検証し、診断用に差し替えたスクリプトを記録するものです。これらの検証記録は「配布判定」において明示的に拒否されます。配布前には、改めて完全な`Build release`の実行が必須となります。

公開プレビューなどを承認のうえ公開すると、「Published installation lifecycle」がさらに10個のケースを実行します。ここでは、ローカルのパッケージ指定（package override）を使用せず、実際のリリースURLからスクリプトやパッケージを匿名でダウンロードし、チェックサム、タグ、コミットの検証を行い、スクリプトを実行します。また、GHCRのCPUイメージの両方を匿名でプルし、公開されたダイジェスト/コミットを確認した上で、Composeのライフサイクルを実行します。新しいQuick Install URLの推奨は、これらの結果を確認した後にのみ行ってください。アップロードが成功しただけでは、オンラインインストールの検証に合格したことにはなりません。本ワークフローは、選択したチェックアウトと一致する公開済みリリースに対しても手動で起動（dispatch）可能です。

**1.2.0-preview.5** の公開スクリプトとGHCRイメージを使った再検証では、10ケース中8ケースが全工程に合格しました。macOSのIntel版・Apple Silicon版は、インストール、整合性、削除に合格しました。導入後のAPI・画面操作、終了、データを保持した再インストールの検証にはOSの初回起動承認が必要です。[公開経路の検査結果](https://github.com/noguhiro2002/FlintEye/actions/runs/44729094734)

最初の公開検査では、Linux x64のGHCRとmacOS ARM64のスクリプトが、導入前にGitHubの匿名REST APIの利用上限に達しました。公開タグの確認を匿名のGit HTTPS照会に切り替え、同じ配布ファイルとイメージで再検証しました。[最初の公開検査](https://github.com/noguhiro2002/FlintEye/actions/runs/44727482801)

<a id="run-the-harness-locally"></a>
## ローカルでのハーネス実行

ネイティブテストはインストール済み環境を削除します。必ず使い捨てのVMまたはQA専用の新規アカウントを使用してください。デフォルトのインストール環境、スタートアップ登録、および既存のデータディレクトリへの実行は拒否されます。通常のアカウントで `--disposable` を渡さないでください。ソーステストは、既存のFlintEyeインスタンスを停止させることなく、一時的なスナップショットと個別のプロファイル/ポートを作成します。

PythonとNodeを準備し、フロントエンドの依存関係をインストールし、ビルドを行い、`frontend/` から `npx playwright install chromium` を実行してください。QA環境で `python -m pip install httpx==0.28.1` を使用して自動テストの実行環境のHTTPクライアントをインストールします。一致するActionsアーティファクトを新規QA Mac上の `installer-input` に展開した状態で、以下を実行します：

```sh
python packaging/lifecycle.py --method macos-dmg --artifact-directory installer-input --output lifecycle-results/macos-dmg --disposable
```

その他の手法: `windows-exe`, `windows-script`, `macos-script`, `linux-deb`, `linux-deb-script`, `linux-rpm`, `linux-rpm-script`, `linux-systemd`。LinuxパッケージのケースはDocker Engineを必要とします。ソースでは、検証済みのネイティブメディアバイナリを指定する `--method source --media-directory vendor/bin` を使用します。Composeでは `--method compose` または `--method compose-development` を使用し、`--image YOUR_ALREADY_BUILT_IMAGE` を指定します。それぞれがイメージを再構築することなく独自のプロジェクト/ボリュームを作成します。テスト対象と一致する公開ビルドをテストする場合を除き、デフォルトのリリース設定は変更しないでください。

<a id="checks-still-required-on-real-machines"></a>
## 実機でのチェック項目

安定版への昇格前には、[8つのデバイスゲート](RELEASE_CHECKLIST_1_2_0.ja.md)が必須となります：ネイティブメニュー/ウィンドウとアクセシビリティ、macOSの初回起動/カメラ/マイク権限、Windows PCでの削除テスト、USBカメラ/再接続、スリープ、個別のLANクライアント/証明書の信頼、実際のDocker Desktopホストのビデオ、最小サポートOSバージョン、および24時間の動作確認。CIはユーザーのコンピューター上でこれらを承認することはできません。ビルドやブラウザのみのテストから合格と推測するのではなく、証拠を添えて合格、失敗、または未テストを記録してください。
