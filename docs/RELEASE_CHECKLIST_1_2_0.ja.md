専用のテストプロファイル、録画フォルダ、コンテナボリュームを使用してください。プロファイルを保持するテストでは、バックアップされたテストプロファイルを使用します。パスワード、セットアップトークン、秘密鍵、プライベート設定のバックアップ、または個人的な映像を公的な証拠として添付しないでください。ディスクフル、削除、急な停止、および電源切断のテストには使い捨てデータを使用し、ユーザーデータが含まれるコンピュータの電源を切るのではなく、VM内で電源切断をシミュレートしてください。

必須のデスクトップデバイスのカバー範囲には、Windows x64、M1 Mac、Linux x64が含まれます。以下に記載するPC/モバイルブラウザの組み合わせも実行してください。その他のOS/CPUターゲットは個別に記録してください。ARM64/Intelビルドが成功しただけでは、そのターゲットの実機での動作を確認したことにはなりません。これらのコミュニティパッケージについては、文書化されたOS承認手順に従ってください。Developer IDの署名/公証は後回しとなります。

単体インストーラーとワンコマンド版は、同じ成果物で試してください。コンテナは対応する `containers/container-amd64.tar.gz` または `containers/container-arm64.tar.gz` を読み込み、開発ガイドに記載したローカルイメージタグを使います。[コンテナを公開前に検証する手順](DEVELOPMENT_1_2_0.ja.md)

## 1. Windows起動 — `windows-owner-startup`

- [ ] WinError 2が報告されたWindowsコンピュータ上で、EXEインストーラーとローカルアーティファクトによる1コマンドインストールを同じビルドから比較する。個別のPython、Node.js、Git、FFmpeg、MediaMTXのインストールは不要。
- [ ] 新規プロファイル、保持された設定済みプロファイル、および中断された初期セットアップで繰り返す。管理者未設定なら初回設定、設定済みなら通常ログインに進むこと、および既存のパスワード/設定/録画が保持されたプロファイルの場合でも維持されることを確認する。
- [ ] 変更されたインストールディレクトリ、スペース/非ASCII文字を含むパス、異なる作業ディレクトリからの起動を確認する。二重起動が2つ目のサーバーを作成しないことを確認する。
- [ ] 実際のUSBカメラを選択する。バンドルされたMediaMTXが起動し、ライブビューでビデオが表示され、完了した録画の再生/ダウンロードが可能であり、終了操作で所有するAPI/メディアプロセスが閉じることを確認する。繰り返される空白のコンソールウィンドウが表示されないこと。
- [ ] 元の操作を再現し、結果を記録する：WinError 2が発生しないこと。4294967291を含むその他のキャプチャエラーは個別に記録・調査する。カメラ映像なしでページが読み込まれる状態は、このゲートを通過しない。

## 2. Windows削除 — `windows-owner-removal`

- [ ] Windowsの設定→アプリを使用して、実行中、録画中、および監視停止後にFlintEyeを削除する。報告されたコンピュータ上の元のError 32を再確認する。
- [ ] 通常の削除により、最後の録画が完了し、動作中の全プロファイルと、それらが所有するプロセス/待受が停止され、バンドルされたアプリケーション、FastAPIランタイム、FFmpeg/FFprobe、MediaMTXが削除される。別のアプリケーションのプロセスは影響を受けないこと。
- [ ] ログイン時のスタートアップエントリと、このインストールによるLANファイアウォールルールが削除される（停止済み/カスタムプロファイルのルールを含む）。別のインストールのルールは維持されること。必要なファイアウォールの承認を拒否すると削除がキャンセルされ、再試行が可能であること。
- [ ] 設定と録画はデフォルトで保持され、再インストール後に使用可能であること。明示的なデータ削除を選択した場合のみ、データが削除されること。正常な削除後に、重複または壊れたアプリ削除エントリが残らないこと。
- [ ] 使い捨て環境において、同時削除、重複削除、アンインストール用データファイルが別プロセスに使用されている状態、および権限拒否をテストする。失敗した場合はブロッカーを特定し、データを保持したままブロッカー削除後に再試行が可能であること。関係のないプロセスを強制停止させないこと。

## 3. デスクトップコントロールとアクセシビリティ — `native-menus-and-accessibility`

- [ ] Windows x64、M1 Mac、Linux x64上で、トレイ/メニュー/コントロールウィンドウのOpen、Start、Stop、Restart、Quitを実機上で操作する。macOSではDockからの終了もテストし、Linuxではトレイとコンパクトなフォールバックウィンドウをテストする。
- [ ] 録画中にStopをクリックすると、カメラ/サムネイル/プレイヤーが一時停止し、API/設定を利用可能な状態のまま最後の録画が完了すること。設定を保存してアプリケーションを再起動しても、Always resumeが明示的に有効になっていない限り、停止設定が保持されること。
- [ ] Stop後の終了を含め、終了するとアプリと所有するメディアプロセスが終了し、他のアプリがカメラを使用していないテスト環境ではカメラインジケーターが消灯すること。再起動時は保持された設定を使用すること。ブラウザウィンドウを閉じるだけでは監視は継続すること。
- [ ] ログイン時のスタートアップと監視の再開が個別の設定として機能すること。アイコン、表示状態/進捗、高DPI、ライト/ダークの外観が理解可能であること。ネイティブとWebのステータスが一致すること。意図的なStopは、カメラなしやストリーム異常とは区別されること。
- [ ] キーボード操作とスクリーンリーダー(Narrator/VoiceOver)が、ブラウザ内の初期パスワードフィールド、入力内容の確認メッセージ、操作ボタンに到達できること。英語のオンボーディングはスキップ/再開が可能であり、ストレージとビューアーパスワードの制御が見つけられ、使用できること。

## 4. LAN PC — `lan-pc`

- [ ] 物理的に分離されたクライアントから、Windows Edge/Chrome、macOS Safari/Chrome、Linux Firefox/Chromeをテストする。ガイドに従ってエクスポートされたCAをインストール/信頼し、証明書のフィンガープリントを照合し、選択したHTTPS URLを使用する。
- [ ] 初期セットアップにはオーナーのトークンが必要であること。期限切れ/再利用されたトークンや過剰な試行は拒否されること。管理者およびビューアーとしてサインインする。ビューアーは設定を変更できず、匿名クライアントはAPIや内部メディアエンドポイントを通じて認証をバイパスできないこと。
- [ ] ライブビュー、マルチビュー、録画一覧/再生/ダウンロードが、実際のカメラ映像を使用してHTTPS経由で機能すること。ログインまたはページ到達のみでは不十分。アプリ/サーバー/クライアントの再起動後も繰り返す。サーバーIPが変更されない限り、URLが使用可能であること。
- [ ] 証明書の更新/期限切れの復旧、IP変更、複数のネットワークインターフェイスを確認する。選択されたインターフェイスのみが公開されること。IPが変更された場合は、ローカル設定と更新された接続ガイドから復旧すること。古いIPのURLが有効であると期待しないこと。
- [ ] ファイアウォールの拒否/再試行および拒否されたソースネットワークを確認する。Windowsの許可は意図されたプライベートネットワークのソースに限定されること。承認が拒否されてもローカル復旧が機能すること。クライアントCAの信頼を削除/再インストールし、期待される信頼状態を確認する。

## 5. モバイルLAN — `lan-mobile`

- [ ] iPhone Safari、iPad Safari、Android Chromeを個別にテストし、各デバイス/OS/ブラウザバージョンを記録する。Linux WebKitやモバイルサイズのデスクトップウィンドウはこのゲートを通過しない。
- [ ] iPhone/iPadでの完全な信頼を含む、証明書ガイドに従うこと。意図的な信頼の後にHTTPSが機能し、FlintEyeの信頼が削除された場合に期待される失敗を示すこと。
- [ ] 管理者/ビューアーのログインと制限、ライブビュー、マルチビュー、録画一覧/再生/ダウンロードが、実際のカメラ映像と操作可能なタッチコントロールで機能すること。アプリ/デバイスの再起動後に同じIP URLで再確認する。セッションが期限切れの場合は再ログインすること。

## 6. カメラ、ストレージ、長期実行 — `physical-cameras-and-long-run`

- [ ] 2台の実際のUSBカメラを同時に使用し、ライブビュー、マルチビュー、録画を行う。カメラモデル/解像度/fpsを記録する。サムネイルのタイムスタンプと実際のビデオを比較し、古い画像とカメラの健全性を区別する。キーフレーム間隔の長いlong-GOP映像も、Live ViewとMultiviewを並行して確認する。
- [ ] カメラの取り外し/再接続およびスリープ/復帰をテストする。中断と復旧の時間、有効なエラー、意図しないカメラのオン/オフループを記録する。終了後、所有するキャプチャプロセスとカメラインジケーターが停止すること。
- [ ] 別途24時間の2カメラテストを実行する。開始/終了時間、意図した停止、予期せぬギャップ/再起動、録画数、CPU/メモリおよびストレージの動作を記録する。短時間のテストではこの項目は合格しない。
- [ ] 完了したクリップを最初、中間、最後付近で再生/ダウンロードする（停止/終了後の最後の完全なセグメントを含む）。表示される録画の長さ/終了日時/タイムゾーンを確認する。急な停止テストにおいて、不完全なファイルが正常に終了したとマークされないこと。
- [ ] 初期の7日間の保存期間と、空き容量に基づいた容量提案を確認する。使い捨てテスト録画において、期間と容量制限を個別に実施する：最初の制限が、関連のないファイルやアクティブなファイルではなく、対象となる古い完了録画の削除をトリガーすること。
- [ ] 録画フォルダを変更する：古い録画がデフォルトで表示/再生可能であり、オプションで非表示にできること。保存先の変更だけで既存ファイルが移動されないこと。以前の場所を非表示にしても、その場所のスケジュールされたクリーンアップが無効にならないこと。テストデータを用いて、満杯、切断、書き込み不可のストレージを確認する。

## 7. LinuxパッケージとDocker Engine — `linux-native-and-docker`

- [ ] 専用のLinux OS環境で、DEB/APTおよびRPM/DNFのインストール、更新、削除をテストする（保持されたデータと通常終了を含む）。ホスト対VMを記録する。コンテナのみのパッケージの簡易テストでは、OS/サービス統合を確立したことにはならない。
- [ ] SSH経由で、プライベートトークンのセットアップを完了し、正しいアドレスを見つけ、通常通り停止する。デスクトップログインなしでsystemdの開始/停止/再起動を確認する。WebRTCルーティングを個別に記録する。HTTPのみのSSHトンネルはビデオ接続の証拠にはならない。
- [ ] Linux Docker Engine上で、一致するロード済みイメージとバージョン管理されたCompose構成、UID/GID 10001、専用の永続ボリュームを使用する。初期セットアップ、実際の入力/ライブ/録画/再生、およびコンテナ再作成がアカウント/証明書/設定/録画/停止設定を保持すること。
- [ ] 通常のCompose停止/SIGTERMにより最後の録画が完了してインデックス化され、所有プロセスが閉じられ、再起動が可能であること。最後のクリップをデコードする。終了コード143や内部の健全性チェックのみでは不十分。文書化された互換性のあるバックアップを使用して、固定バージョン更新/ロールバックを確認する。デスクトップ/サーバーのデータディレクトリとポートは分離しておくこと。

## 8. Docker Desktop — `docker-desktop-host-video`

- [ ] 実際のWindowsおよびmacOSホスト上で、一致するロード済みイメージと`compose.desktop.yaml`を使用する。ホストブラウザで`http://127.0.0.1:18080`を開き、セットアップ/ログインを完了する。
- [ ] 到達可能なIP/RTSPカメラを手動で登録し、ホストブラウザで実際のWebRTCビデオ、マルチビュー、録画/再生/ダウンロードを確認する。VM内のcurl/健全性チェックでは不十分。この構成は、USB転送、ONVIFマルチキャスト検出、LANサーバーアクセスを提供しない。
- [ ] 同じプロジェクトとボリュームを使用して、停止/再作成/再起動を行う。最後の録画の完了、保持されたアカウント/設定/録画、および停止設定を確認する。コンテナがデスクトップGUI/トレイの要件なしで起動すること。
