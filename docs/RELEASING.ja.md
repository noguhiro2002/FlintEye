<a id="source-first-public-development"></a>
## ソースコードで試すプレビュー版のパブリック開発

公開履歴は **1.1.1 のソーススナップショット** から始まります。現在の開発プレビューは **`v1.2.0-preview.7`** です。公開開発プレビューには、成功した完全なビルドと、ライセンスおよびソースコードの確認が必要です。安定版の配布には、以下の実機での受入テストが追加で必要となります。旧非公開リポジトリの履歴を持つ場合は、公開リポジトリを新しいディレクトリにクローンしてください。

通常のプッシュでは **Distribution checks** が走ります。`main` にバージョン定義、フロントエンドの依存定義・インストール/監査スクリプト、Linux パッケージの動作確認、ビルドワークフローの変更が入ると、**Build release** も自動で始まり、インストーラーと検証済みコンテナーを `release-bundle` にまとめます。それ以外の再ビルドは手動で実行してください。公開リポジトリのビルドログは閲覧でき、成果物は GitHub にサインインすると取得できます。Releases と GHCR への配布には **Publish tested release** を使います。カメラの認証情報や録画、個人の設定は CI の入力やログから除いてください。

**Publish tested release** は以下のチャネルをサポートします：

| 要件 | `private-test` | `public-preview` | `stable` |
| --- | --- | --- | --- |
| リポジトリ | プライベート | パブリック | パブリック |
| デフォルトブランチで全対象のビルドが成功し、アプリとビルドの入力が一致すること | 必須 | 必須 | 必須 |
| リポジトリ変数 | なし | `PUBLIC_PREVIEW_ENABLED=true` | `PUBLIC_RELEASE_ENABLED=true` |
| ライセンスおよびソースコードの確認 | 保留中の場合あり | 必須 | 必須 |
| 実機での受入テストの完了 | 保留中の場合あり | 保留中の場合あり（要開示） | 必須 |
| 埋め込みチャネル | 内部テスト | `preview` | `stable` |
| GitHubリリース | 通常のテストリリース | **プレリリース**（Latestではない） | 通常リリース（Latest） |
| イメージタグ | 正確なプレビューのみ | 正確なプレビューのみ | バージョンおよび `latest` |
| コマンドインストーラー | 除外 | 含まれる（ピン留めされたプレビュー） | 含まれる（ピン留めされた安定バージョン） |

パブリックフラグのデフォルトは `false` です。要求された配信チャネルでのみ有効化してください。ユーザーがインストール経路や実機をテストできるように、パブリックプレビューを公開することができます。受入テストが保留中の間は `device_tests_confirmed` を false のままにしてください。リリースノートと配信マニフェストにその旨を記載する必要があります。CIチェックを、完了した実機受入テストとして説明することは決して行わないでください。安定版の公開には、引き続き Windows x64、M1 Mac、Linux x64 が必要です。これには、カメラキャプチャ、録画・再生、GUI終了による所有プロセスの停止、およびバンドルされたプログラムを削除しつつデータを保持する Windows のアンインストールが含まれます。[受入チェック](ACCEPTANCE.ja.md)を参照してください。

<a id="ghcr-setup"></a>
## GHCRのセットアップ

イメージは `ghcr.io/noguhiro2002/flinteye` を使用します。ディストリビュージョブのみが `packages: write` を受け取り、`GITHUB_TOKEN` を使用します。Docker Hubの認証情報や個人の公開トークンは不要です。OCIのソース/ドキュメントラベルは、パッケージをこのリポジトリに関連付けます。

GitHubは初期状態でパッケージをプライベートとして作成します。リポジトリの可視性とパッケージの可視性は別個のものです。そのため、公開は2つの明示的なフェーズに分割されます：

1. **prepare:** 再ビルドを行わずにテスト済みのイメージアーカイブをアップロードし、ドラフトリリースを作成します。チェックサム、ソースコミット、アーキテクチャ、およびイメージダイジェストを検証します。この段階では、最初のGHCRパッケージはまだプライベートである可能性があります。
2. パッケージ設定でリポジトリの関連付けを確認し、対象のパブリックパッケージを **Public** に変更します。これにより検証済みコンテナが公開されるため、準備フェーズの開始前であっても、ライセンス/ソースレビューおよび選択したチャネルの受入要件が適用されます。プライベートテスト用のパッケージはプライベートのままにしてください。
3. **publish:** 同じビルド実行ID、ソースコミット、チャネル、およびプレビュー番号で再実行します。アップロードされたアセットとコンテナーのレシートを再確認し、ドラフトを公開します。このフェーズでは、パブリックチャネル向けの非公開パッケージは拒否され、成果物の再ビルドや置き換えは決して行われません。

ワークフローは可視性を自動的には変更しません。パブリックイメージでは匿名プルが許可されますが、プライベートテストには許可された `read:packages` の認証情報が必要です。標準のGitHubホステッドランナーが使用され、より大きな有料ランナーは設定されていません。ビルドする前に、現在のストレージ制限とランナーの可用性を確認してください。

公式リファレンス：[GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)。

<a id="version-and-source-of-truth"></a>
## バージョンと信頼できる情報源（SoT）

`flinteye_app/_version.py` は、`VERSION`（数値の `X.Y.Z`）、`RELEASE_VERSION`（例：`1.1.3-preview.1`）、および `RELEASE_CHANNEL`（`source`、`preview`、または `stable`）を保持します。インストーラーのファイル名、Inno Setup、およびDEB/RPMのメタデータには数値バージョンを使用し、ダウンロードURL、アップデートの比較、およびイメージタグには完全なリリースバージョンを使用します。これらの値は、テスト済みのビルドマニフェストと一致している必要があります。ソーススナップショットは `source` チャネルを使用し、インストーラーのアップデートは宣伝しません。
既存のリリースやイメージバージョンを上書きしないでください。

`packaging/vendor-lock.json` は、ソースURLとSHA-256ハッシュを修正します。
FFmpeg、x264、FreeType、HarfBuzz、およびMediaMTXは、これらの検証済みのソースからビルドされます。
MediaMTXのビルドでは、コンパイル済みのRaspberry Pi CSIヘルパーが除外されますが、FlintEyeのUSB/IP入力は引き続き利用可能です。
埋め込みHLSアセットは、ピン留めされたアップストリームソースのハッシュに対して検証されます。
Goモジュールはアップストリームのgo.sumを使用し、保持されるソースツリーにベンダー管理されます。

Pythonの依存関係セットは `packaging/constraints.txt` で制約されており、npmはパッケージロックを使用します。
依存関係を意図的に更新してから、テストと新しいリリースビルドを実行してください。

`npm ci` では、picomatch 4.0.7 の GHSA-fc5q-39xc-vjpf に対するローカル修正を適用します。ワイルドカードの星を含む繰り返し拡張パターンには、既存の文字列照合への切り替え処理を使います。適用時に上流ファイルのハッシュと修正内容を確認します。`npm run audit` は全依存を調べ、この問題が報告されたすべてのコピーに修正がある場合だけ、当該問題を対応済みとして扱います。ほかの High/Critical の指摘や監査サービスのエラーがあればビルドは停止します。picomatch 更新時にローカル修正の要否を見直してください。攻撃パターン、通常のビルド用パターン、監査の除外条件は回帰テストで確認します。[上流のアドバイザリ](https://github.com/advisories/GHSA-fc5q-39xc-vjpf)。

<a id="build-and-test"></a>
## ビルドとテスト

1. `flinteye_app/_version.py` でアプリのバージョン、配布バージョン、チャネルを設定します。同じアプリバージョンのプレビューを更新するときは、プレビュー番号を上げます。
2. バージョン変更を `main` に反映し、GitHub Actions で **Build release** の結果を確認します。同じバージョンを再ビルドするときは、デフォルトブランチを選び、診断オプションを外して手動実行します。
3. **release-bundle** をダウンロードし、ライセンスおよび対応するソースを確認し、完了した[受入チェック](ACCEPTANCE.ja.md)と保留中の受入チェックを記録します。
4. ビルド実行IDとコミットSHAを保持します。公開にはそれらのアーカイブされた成果物が使用され、再ビルドは行われません。

ネイティブマトリクスビルドは、一致するランナー上でWindows x64/ARM64およびmacOS Intel/ARM64をビルドします。Windowsは、アクティブなAPIを使用して実際のEXEインストーラーとアンインストーラーを実行し、停止、バンドルされたファイルの削除、およびデフォルトデータの保持を検証します。この自動化されたチェックは、物理カメラの受け入れテストの代わりにはなりません。
WindowsとmacOSはPython 3.14.10を使用しており、両方のCPU向けのインストーラービルドが存在します。
Linuxパッケージは、Ubuntu、Enterprise Linux、および64ビットRaspberry Pi OS向けの更新されたRocky Linux 9内でビルドされます。バンドルされたランタイムには GLIBC_2.35 シンボルが必要です：DEBには libc6 2.35以降が必要ですが、RPMには libc.so.6(GLIBC_2.35)(64bit) 機能が必要であり、必要に応じてdnfが古いRocky 9インストールのランタイムをバックポート版にアップグレードします。
Linuxビルダーおよびサーバーイメージは、ピン留めされたPython 3.13ランタイムを使用します。
GitHubランナーの可用性と最小OSハードウェアチェックは個別の懸念事項であり、新しいランナーが存在しても古いOSが動作することは証明されません。

完全なリリースバンドルの場合、**desktop_only** のチェックを外したままにします。
Windows/macOSのパッケージングを診断する場合にのみこれを選択してください。その実行では個別のデスクトップ成果物が生成され、公開には使用できません。

ソースからのビルドには、特に初回実行時にかなりの時間がかかる場合があります。ビルド成果物は30日間保持されます。
ご使用のGitHubプランでランナーを利用できない場合は、ご自身のマシンで同等のネイティブビルドを実行し、完全なリリースマトリクスを要求する前にランナーの可用性を解決してください。

<a id="local-native-build"></a>
### ローカルのネイティブビルド

M1 / Apple Silicon Macの場合は、[local DMG guide](LOCAL_MACOS_BUILD.ja.md)を使用してください。これにより、分離されたビルドの準備、共有 Settings インターフェースの再ビルド、およびGitHub Actionsなしでのインストール済みDMGとMediaMTXパスのリカバリのテストが行われます。これによりローカルテスト成果物が生成されますが、公開はされません。

Windows/macOSでは、Python 3.14.10、Node.js 22.12+、Go 1.27、C/C++コンパイラ、make、CMake、Ninja、pkg-config、Meson、およびNASM（x64）をインストールします。
WindowsはMSYS2 UCRT64またはCLANGARM64を使用します。macOSは `MACOSX_DEPLOYMENT_TARGET=14.0` でビルドします。
ネイティブLinuxパッケージ用の以下のDockerビルダーを使用してください。ピン留めされたPython 3.13.18ソースをコンパイルします。

Windows ARM64の場合は、Visual Studio C++ ARM64ツール、Rust、およびネイティブのStrawberry Perlもインストールしてください。以下の依存関係コマンドを実行する前に、ネイティブのARM64 Pythonを使用して`python packaging/build_windows_crypto.py`を実行してください。固定したcryptographyのリリースにはWindows ARM64用のwheelが含まれていないため、このヘルパーを使用して、公式のソースハッシュが`packaging/vendor-lock.json`に固定されている静的リンクされたOpenSSL 3.5.9に対してネイティブwheelをビルドおよびインストールします。ソース、ライセンス、およびビルド情報はバンドルに保持されます。再試行の際は、新規のチェックアウトを使用してください。[cryptographyビルド手順](https://cryptography.io/en/stable/installation/#building-cryptography-on-windows)および[OpenSSL Windows手順](https://github.com/openssl/openssl/blob/openssl-3.5.9/NOTES-WINDOWS.md)を参照してください。

```sh
python -m pip install -c packaging/constraints.txt -r requirements.txt -r packaging/requirements-build.txt meson==1.9.1 ninja==1.13.0
bash packaging/build_vendor.sh
python packaging/build_bundle.py --vendor vendor
python packaging/smoke_desktop_bundle.py
```

`/DAppVersion=X.Y.Z /DAppArch=amd64`（または `arm64`）を使用して、Inno SetupでWindowsインストーラーをコンパイルします。
macOSバンドルビルダーは、アプリケーションのショートカットを含むDMGを作成します。

Linuxの場合は、ターゲットCPU上でパッケージセット全体をビルドします：

```sh
docker buildx build -f packaging/LinuxBuilder.Dockerfile --target artifacts --output type=local,dest=dist .
```

<a id="redistribution-material"></a>
### 再配布用の資料

すべてのネイティブターゲットには、対応するソースとライセンスZIPが含まれています。
Linuxパッケージには、署名入りの正確なバージョンのRockyソースRPM、およびLGPLライブラリを含め、バンドルにコピーされたシステムライブラリに関する通知も保持されます。デスクトップバンドルからは、未使用のインタラクティブな `readline` モジュールが除外されます。
Dockerビルドは、FFmpeg/FFprobeの依存関係のクロージャの正確なソースバージョンをキャプチャし、そのDebianソースパッケージをエクスポートします。
MediaMTXの修正されたソースツリーとベンダー管理された依存関係は個別にエクスポートされます。
必要な対応ソースの代わりにアップストリームのホームページリンクを使用しないでください。

配布前に、Pythonインタプリタ、Tcl/Tk、OSライブラリ、およびその他のバイナリ依存関係について、生成されたインベントリを確認してください。
古いリリースについても、ソース/ライセンスアーカイブをダウンロード可能な状態に維持してください。FFmpeg `--enable-nonfree` を有効にするビルドは失敗します。

<a id="source-cache-option"></a>
### ソースキャッシュのオプション

Dockerは、すでにダウンロードされたパブリックなMediaMTX/HLSアーカイブのみを含むBuildKitの名前付きコンテキスト `vendor-downloads` を使用できます。
ビルドでは引き続きピン留めされたハッシュが検証されます。これにより、Docker内での直接のソースダウンロードが利用できない環境でのテストが可能になります：

```sh
docker build --build-context vendor-downloads=/path/to/verified-public-source-cache -t flinteye:development .
```

認証情報、ランタイム設定、または録画をそのキャッシュに入れないでください。

<a id="publish-the-tested-build"></a>
## テスト済みビルドの公開

必要な確認がすべて済んだら、デフォルトブランチから **Publish tested release** を実行します。全対象が成功したビルド実行 ID と `public-preview` を選び、ビルドに含まれるプレビュー番号を入力します。`1.2.0-preview.7` なら `7` です。準備と公開で同じビルド実行 ID と公開コミットを使います。ライセンスとソースを確認し、配布用フラグと実機確認の結果を設定してください。

ビルドコミットは、インストーラー、コンテナラベル、リリースタグの信頼できる情報源（ソースオブトゥルース）であり続けます。新しい公開コミットで変更できるのは、READMEファイル、`docs/` 配下のMarkdown、Compose、リリース公開のスクリプト/ワークフロー、あるいはそれらに特化したテストのみです。アプリケーションコード、依存関係、ネイティブビルドの入力、コマンドインストーラースクリプト、イメージ、または LICENSE の変更には、新しい完全ビルドが必要です。両方のコミット識別子が配信マニフェストに記録されます。更新されたドキュメントは再現性のある形でパッケージ化され、準備フェーズと公開フェーズのチェックサムが一致するようにします。また、安定版の公開には、安定した埋め込み識別子と完全なビルドが必要です。プレビュー版を安定版としてリネームすることはできません。

添付の `documentation.zip` では、インストール手順内のバージョンとURLを、今回公開するプレビュー版に合わせます。過去の修正履歴と元のソースアーカイブは、それぞれのバージョンを維持します。メインREADMEの推奨版は、公開URLから匿名でインストールする検証の結果を確認してから変更します。ドキュメントのチェックサムを同一に保つため、prepareとpublishでは同じ公開用コミットを使ってください。

GitHubの`GITHUB_TOKEN`では、ワークフローファイルが現在のデフォルトブランチと異なるテスト済みコミットに対してリリースを作成することはできません。このガードは、イメージをアップロードする前に該当するケースを拒否します。ワークフローを変更した後は、完全なビルドを実行することを推奨します。途中で停止した配布処理によってイメージが既にアップロードされている場合は、メンテナンス担当者が承認済みアカウントを使用してリリースを完了させることができます。その際、元のビルドと公開用コミットからファイルを再構築し、すべてのチェックサムが保存された`distribution-receipt`と一致することを確認し、既存のコンテナダイジェストを検証した上で、元のビルドコミットに対してリリースを公開してください。バージョン管理されたイメージを上書きしたり、より広範なパーソナルアクセストークンをCIに追加したりしないでください。ドラフトを確認するには、認証済みのリリースリストまたはリリースIDを使用してください。タグエンドポイントは公開されたリリースのみを返します。[GitHubのRelease APIと権限](https://docs.github.com/en/rest/releases/releases)。

ワークフローは、すべてのアーカイブファイルを検証し、テスト済みのamd64/arm64コンテナーアーカイブを読み込み、CPUとソースの同一性をチェックし、マルチプラットフォームのマニフェストを作成し、レジストリダイジェストを記録します。リリースアセットには、インストーラー、対応するソース/ライセンス、バイリンガルのガイド/ノート、Compose、元のビルド情報、ディストリビューションメタデータ、チェックサム、および（パブリックチャネル向けには）ピン留めされたコマンドインストーラーが含まれます。

既存のタグ、インストーラーの内容、およびバージョン付きのイメージタグが上書きされることは決してありません。失敗したprepare操作により、アップロードされたイメージやドラフトが残る可能性があります：回復の前にその出所を検査し、保持してください。同じビルドに対して正常に準備されたドラフトは、第2フェーズによって公開できます。安定版の公開のみがコンテナーの `latest` タグを更新します。

<a id="user-updates"></a>
## ユーザーのアップデート

プレビュー版のデスクトップビルドは、フルバージョンを使用して公開されたプレビュー版と安定版をチェックします。安定版はプレビュー版を無視します。アップデートリンクは正確なタグを指します。ソーススナップショットはGitからアップデートされます。ユーザーは監視を停止した後に手動でインストールします。
Docker管理者はイメージのバージョンを変更し、`docker compose pull` に続いて `docker compose up -d` を実行します。
以前のリリース成果物を保持し、設定の移行/ロールバックの要件をドキュメント化してください。


<a id="1-2-0-publication-gate"></a>
## 1.2.0 公開ゲート

[インストールライフサイクルチェック](INSTALLATION_QA.ja.md)は配布ビルドで毎回実行します。これには、ビルド後の assembly 前に同じコミットのインストーラーとイメージを用いて、インストール、API、GUI、終了、アンインストール、再インストールを含む36のテストケースを行います。不足や失敗がある場合、リリースバンドルはブロックされます。macOSの初回起動ポリシー拒否が確認された場合は明示的に手動確認が必要で、API/GUIは未テスト扱いとなります。パブリック配布では、実際の匿名リリースダウンロードと GHCR プルをテストする別のワークフローが開始されます。新しい Quick Install バージョンを推奨する前にそのワークフローを確認してください。ネイティブ権限、カメラ、その他デバイスのゲートは別個のままです。

1.2.0 開発サイクルでは、自動化された結果と物理デバイスの結果を `packaging/acceptance-1.2.0.json` に個別に記録し、テスト済みの正確なアプリケーションコミットに紐付けます。パブリック開発プレビューには「全ネイティブアーキテクチャ」での合格が必要であり、物理デバイスの項目は保留のままにできる場合もありますが、その際は必ず開示する必要があります。失敗した項目や証拠の欠如は公開をブロックします。いずれかの物理デバイスの項目が保留中の間は `device_tests_confirmed=false` を維持してください。完全な証拠なしにこれを確定させることは拒否されます。安定版の配布には、記録された9項目すべてが合格し、かつ明示的なデバイス確認が必要です。どちらのパスも、アプリやビルドの入力をテストしたものと置き換えたり、ライセンス/ソースレビューをスキップしたり、既存のバージョンを上書きしたりすることはできません。プレビュー版は UNDER DEVELOPMENT であり、GitHub プレリリースとして扱われ、Latest やコンテナの `latest` タグは更新されません。[Full 1.2.0 acceptance](DEVELOPMENT_1_2_0.ja.md)
