# コンピューターでの最終確認

<a id="obtain-the-exact-build"></a>
## 正確なビルドの取得

1. レポジトリのデフォルトブランチにレビュー済みの変更をプッシュします。
2. **Actions → Build release → Run workflow** を実行します。
3. 成功した実行の **release-bundle** アーティファクトをダウンロードします。
4. `build-manifest.json` から、実行ID、コミットSHA、バージョンを記録します。
5. 各コンピュータで、`public` ディレクトリから一致するパッケージをインストールします。

このパブリックリポジトリ内のビルドアーティファクトはリポジトリの閲覧者に表示されますが、ダウンロードにはGitHubへのサインインが必要です。これらは未承認の開発ビルドであり、公開されたリリースではありません。
アーティファクトは30日後に期限切れになります。テスト中はローカルコピーを保持してください。
ビルド内のインストールスクリプトは、そのバージョンが公開されるまで機能しないリリースURLを指しています。この段階では、ダウンロードしたEXE/DMG/DEB/RPMを直接テストしてください。

Python、Node.js、Git、FFmpeg、MediaMTXがインストールされていないクリーンなアカウント/VMを使用してください。
テストカメラと使い捨ての録画フォルダを使用してください。容量/保持期間のチェックにより、条件を満たすテスト録画が意図的に削除されます。

## ターゲットマトリックス

**pass**（合格）、**fail**（不合格）、**not tested**（未テスト）を個別に記録します。ビルドの成功はOSを保証するものではありません。

| OS | CPU | インストール/セットアップ | ライブ/録画/再生 | アップデート/データ保持 |
| --- | --- | --- | --- | --- |
| Windows 10 22H2 / Windows 11 | x64 | | | |
| Windows 10 22H2 / Windows 11 | ARM64 | | | |
| macOS 14+ | Intel | | | |
| macOS 14+ | Apple Silicon | | | |
| Ubuntu 24.04 | x64 / ARM64 | | | |
| Rocky Linux 9 / 10 | x64 / ARM64 | | | |
| Raspberry Pi OS Bookworm, 64-bit, Pi 4/5 | ARM64 | | | |
| Docker Engine on Linux | amd64 / arm64 | | | |

一部のターゲットがテストされていない場合は、検証済みとしてマトリックス全体を宣伝するのではなく、ビルドを開発プレビュー版として維持してください。
実際のRaspberry Piのカメラ台数/解像度/fpsを記録し、普遍的なカメラの制限を外挿しないでください。

<a id="desktop-checklist"></a>
## デスクトップのチェックリスト

- [ ] インストーラーが開発者ツールなしで動作する。未署名アプリの確認は、ドキュメント化されたOSのフローに従う。
- [ ] 管理者パスワードの作成、キャンセル、再開が機能する。デフォルトのパスワードによるアクセス権の付与はない。
- [ ] 初回起動時の英語ツアーが開き、スキップと再開が機能する。
- [ ] USBの権限と検出が機能し、IPカメラがその資格情報を使用して接続できる。
- [ ] Live View、カメラの録画、録画の一覧表示、ダウンロード、再生が機能する。
- [ ] macOSでは、DMGからアプリをコピーし、DMGを取り出し、終了/再起動を行い、MediaMTXとUSBカメラが稼働し続けることを確認する。停止したアプリを移動し、同じプロファイルで再起動し、録画/設定が引き続き利用可能であることを確認する。代替アプリのインストール後、ログイン時自動起動を再度テストする。
- [ ] ビューアーアクセスには設定されたビューアーパスワードが必要であり、設定を変更できない。
- [ ] 初期ストレージの提案は min(50 GB, 空き容量の半分) であり、保持期間は7日である。
- [ ] 容量ベースおよび古さベースの両方のクリーンアップにより、条件を満たした完了済みのテスト録画のみが削除される。
- [ ] フォルダの変更により、デフォルトでは古い録画が表示されたままになり、オプションをオフにすると非表示になる。
- [ ] 削除/再接続されたディスクや空き容量不足により、理解しやすい動作が発生する。
- [ ] 非ASCIIユーザー名、スペースを含むパス、カスタム録画フォルダが機能する。
- [ ] ブラウザを閉じてもモニタリングが実行され続け、明示的な終了によって停止し、二重起動によって2つのサーバーが作成されることはない。
- [ ] ログイン時自動起動が機能し、手動でのスリープ/ログアウト/停止の動作が把握されている。
- [ ] アップグレードによって設定と録画が保持され、通常のアンインストールによってデータが保持される。Windowsでは、APIがアクティブな状態でアンインストールを行う：API/メディアプロセスが停止し、バンドルされた実行ファイルが削除されることを確認する。macOSでは、トレイ/コントロールウィンドウとDockから個別に終了する：カメラがオフになり、所有しているメディアプロセスが終了することを確認する。
- [ ] LAN視聴ではHTTPSを使用し、認証が必要である。内部メディアエンドポイントを匿名で使用することはできない。

<a id="server-checklist"></a>
## サーバーのチェックリスト

- [ ] DockerがUID/GID 10001として起動し、コンテナの再作成後もデータを保持する。
- [ ] ヘッドレスの初回起動トークンはプライベートかつ使い捨てであり、ログに記録されない。
- [ ] 固定バージョンを使用して、Composeのプル/アップデートおよびロールバックが機能する。
- [ ] systemdが、独自のアカウント/データディレクトリを使用して、デスクトップログインなしで起動する。
- [ ] どちらのデプロイメントも、デスクトップインスタンスとポートまたはライブデータディレクトリを共有しない。

<a id="publication-sign-off"></a>
## 公開の承認

ソース/ライセンスアーカイブ、インストーラーのインベントリ、チェックサムをレビューする。
ソースコミットとビルド実行IDが、テストしたものと正確に一致していることを確認する。
承認後にパッケージを編集/再ビルドしない。コードを変更する場合は、新しいビルドと適切な再確認が必要である。

ソースリポジトリはすでに公開されている。このレビューの後でのみ、一致する公開プレビューフラグを有効にし、**Publish tested release** の両方のフェーズを使用する。最初の公開プレビューでは、Windows x64、M1 Mac、Linux x64デバイスの受け入れ（カメラの録画/再生、GUIの完全な終了、データ保持を伴うWindowsのアンインストールを含む）が必要である。該当する場合は、他のプラットフォームを未テストとしてマークする。公開プレビューではGitHub Pre-releaseを使用し、Latestは絶対に使用しない。
公開後、クリーンなコンピュータからのREADMEの1行インストール手順のルートを確認し、宣伝されているすべてのリリースアセットにアクセスできることを確認する。

<a id="monitoring-controls-in-113"></a>
## バージョン1.1.3のモニタリングコントロール

- [ ] すべてのインストーラーで1つのコミットをテストし、「情報」からバージョン、チャネル、コミットを記録する。
- [ ] ネイティブステータスとWebステータスの比較：カメラなし、受信中、録画中、1つ/すべて切断、MediaMTXダウン、利用不可のヘルス、開始中、停止中、停止済み。15秒のストール閾値と、設定済み/ターゲット/受信中/録画中の明確な数値をそれぞれ確認する。
- [ ] 録画中の停止：API/設定が利用可能なままであること、カメラのインジケーターがオフになること、最後のセグメントがインデックス化された後にMediaMTXが停止することを確認する。最後のセグメント全体をデコードし、再起動後に再生する。
- [ ] 停止中に設定を保存し、メンテナンス/リカバリを待ってからアプリケーションを再起動する。モニタリングはデフォルトで停止状態を維持し、「常に再開」の設定によってその動作が明示的に変更される。
- [ ] モニタリングの再開とは別にログイン時スタートアップを検証し、別のインストール/プロファイルのログイン登録を保持する。
- [ ] 容量不足、ストレージの切断、または遅延した完了フックがある状態で、保留中の停止を再試行する。強制終了では警告を発し、未検証の確認記録を保持する必要があり、有効な録画であると主張してはならない。
- [ ] Windows/macOSでは、すべてのトレイ/メニューアクションを物理的にクリックし、高DPI、ライト/ダークモード、キーボード操作を検査する。Linuxでは、トレイが有効なデスクトップとコンパクトなフォールバックウィンドウの両方をテストする。
- [ ] Docker/ヘッドレスは、Tk/トレイ/ログイン登録なしで起動する。Composeの再作成により、アカウント、録画インベントリ、停止状態の設定が保持される。
- [ ] USBの物理的な切断/再接続と、手動でのスリープ/復帰を繰り返す。個別の24時間ソークテスト結果を記録する。短いテストはこの項目に合格しない。

契約の締結、公証、パブリックリリースのプロモーションは、この開発ビルドテストサイクルの対象外である。
