## Preview.3: macOSインストールフォローアップ

- 公開されているワンコマンドURLは 1.2.0-preview.10 をインストールします。READMEは、アーティファクトベースのテストのために対応するActionsパッケージへのリンクも提供しています。各OSの成果物には独自のバージョン固定スクリプト、`validation-build.json`、および `SHA256SUMS` が含まれているため、テストには数GBのリリースバンドル全体は不要になりました。
- macOSのカメラ検出では、モードを問い合わせる前に `Capture screen` を除外します。ワーカーの起動時に保存されたインデックスを有効なカメラ名に解決し、キャプチャ前にディスプレイや切断されたデバイスの選択を拒否します。対応モードの問い合わせにはカメラ名を使用して、カメラの取り外し時にディスプレイが選択されてしまう競合を回避します。これは繰り返される画面録画のリクエストに対処するためのもので、ネイティブの権限動作については依然として所有者のMacでの再テストが必要です。
- 初期パスワード入力はブラウザ内で行われます。ネイティブのセットアップ支援には正確なプレビュー版が表示されます。バンドルメタデータ、ランタイムネイティブダイアログ、およびDockにはFlintEyeアイコンが使用されます。スクリプトはインストールされた正確なアプリのコピーを登録します。Informationにはプレビュー番号まで表示され、認証付きのRTSPSカメラアドレスと、内部処理用のアドレスを区別できます。
- READMEおよび削除ガイドには、スクリプト、ネイティブパッケージ、Docker、systemd、およびソースの削除手順が記載されており、デフォルトでデータは保持されます。古い `/Applications` のコピーとスクリプトによる `~/Applications` のコピーは共存可能なため、それぞれを削除するか、意図的に保持してください。

## <a name="acceptance-required-before-stable-distribution"></a>公開前に必要な承認 (Acceptance)

専用のプロファイル、記録フォルダ、コンテナボリュームを使用してください。既存のユーザー記録と設定は保持してください。正確なリリース、チェックサム、コミット、OS/CPU、ブラウザ、インストールパス、プロファイル、および手順を記録し、シークレットや個人的な映像は除外してください。

1. Windows x64: ワンコマンドおよびEXE。それぞれ、クリーンなプロファイル、設定済みの保持されたプロファイル、未完了のセットアップ、変更されたインストールディレクトリ、スペースや非ASCII文字を含むパス、古いcwdを使用します。期待されるセットアップとログイン、バンドルされたMediaMTX、実際のビデオ、記録の復号完了、および所有者によるQuitの確認を行います。
2. Windows削除: 実行中、記録中、停止中、重複エントリ、意図的に保持されたアンインストールデータハンドル、権限拒否、および再試行。関連のないプロセスを終了させずに、ロック保持者を特定します。プログラム/プロセス/スタートアップ/所有するファイアウォールの残骸がなく、記録が保持されていることを確認します。所有者の元の症状をテストしてください。合成再現は所有者の環境での回復を証明するものではありません。
3. ネイティブMac M1、Windows x64、Linux: Open/Start/Stop/Restart/Quitの実際のトレイ/メニュークリック、ログイン時のスタートアップ、正しいアイコン、および表示される状態テキスト。VoiceOver/Narratorおよびキーボードは、ブラウザ内のパスワード入力と操作に到達可能でなければなりません。3つのOSファミリーすべてで、x64/ARM64のビルドとスモークテストを実行してください。
4. 物理LAN: Windows Edge/Chrome、Mac Safari/Chrome、Linux Firefox/Chrome、iPhone/iPad Safari、Android Chrome。インストール/削除の信頼性、管理者/ビューアの役割、初期所有権、ライブ/マルチビュー、記録/再生、同一URLでのアプリ/OS再起動。証明書のローテーション/有効期限、IP変更、複数のNIC、ファイアウォールによる拒否、不正な範囲、トークンの有効期限切れ/再利用、レート制限をテストします。実際のデバイス/OS/ブラウザのバージョンを記録してください。
5. 実際のUSBカメラ: 両方の接続デバイス、同時記録、取り外し/再接続、スリープ/復帰、24時間稼働、ストレージのフル/利用不可状態。急な停止/電源喪失のシミュレーションには使い捨てのテストデータとVMを使用します。完了したファイルが再生可能であり、不完全なファイルが誤って終了処理されていないことを確認してください。
6. Linux専用ホスト：実際のapt/rpmインストール、更新、削除、SSHセットアップ/正常終了、およびsystemdの開始/停止。Docker Engine：公開前に一致するロード済みビルドアーカイブを使用して、永続性、SIGTERMによる記録フラッシュ、プロセス・クリーンアップをテストし、承認された公開後にGHCRプルを確認してください。Docker Desktop：ホストブラウザ認証と実際のWebRTC再生。VM内部の健全性チェックだけでは不十分です。

## ビルド、レビュー、ロールバック

Pythonスイート、フロントエンドビルド/ブラウザスイート、ドキュメントチェック、および正確なネイティブパッケージ/コンテナのスモークテストを実行してください。シークレットや映像はコミットされたエビデンスの外に置いてください。ソースのみの単体テストやエミュレータは、必要なハードウェア承認の代わりにはなりません。Terraは、変更された認証とライフサイクルの境界をレビューします。

移行前に、ランタイム/監視のバックアップをプロファイル内の `backup-before-1.2.0` にプライベートで保存します。これらには機密設定が含まれているため、決して課題（issue）に添付しないでください。一致する古いバックアップを復元し、固定された1.1.3パッケージを再インストールする前に、新しいアプリケーションを停止してください。既存の記録とインベントリを保持します。LANアクセスをロールバックする場合は、新しいWindowsファイアウォールルールと古いクライアントの信頼設定を削除してください。自動的なダウングレードやデータ消去は実行されません。

**安定版の配布は、1.2.0 P1の承認ゲートが保留中または失敗している間はブロックされます。** 公開中のUNDER DEVELOPMENTプレビューでは、物理的な承認ゲートが保留されている間も、インストールパスや物理デバイスのテストを目的として、成功した同一コミットのビルドを配布する場合があります。それらの結果は記録とリリースノートで保留中の状態を維持し、物理テストが合格したとは主張しないでください。テスト済みの対応ソース、インストーラー、固定スクリプト、Compose、ライセンス/ソース、およびチェックサムをまとめ、配布してください。古いタグ/アセットを上書きしたり、プレビューに対してイメージ `latest` タグを作成したりしないでください。

## 公開前にワンコマンドインストーラーを検証する

成功したビルドリリース実行の `release-bundle` アーティファクトをダウンロードして展開します。その `public` フォルダには、インストーラー、インストールスクリプト、および `SHA256SUMS` が格納されています。使用する前に、ワークフローのコミットとビルドマニフェストを確認してください。以下の明示的なローカルアーティファクトモードは、公開された 1.2.0 リリースを必要とせず、同じインストーラーとチェックサムチェックを使用します。これはリポジトリのクローンを作成したり、OS の実行承認をバイパスしたりするものではありません。通常のユーザーとして実行し、既存の FlintEye インスタンスを先に終了させ、必要に応じて専用のクリーンな（または保持された）QA プロファイルを使用してください。

Windows PowerShell（展開したバンドルディレクトリから実行）:

```powershell
.\public\install.ps1 -Version 1.2.0-preview.10 -PackageDirectory .\public
```

macOS または Linux（展開したバンドルディレクトリから実行）:

```sh
bash public/install.sh --version 1.2.0-preview.10 --package-directory public
```

このインストールを同じフォルダ内のスタンドアロンインストーラーと比較し、両方の SHA-256 値が一致することを確認してください。バージョンとソースコミットは固定してください。パブリックダウンロードコマンドは、1.2.0-preview.10 開発リリースに固定されます。安定版へのプロモーションは物理的な承認を待つ必要があります。GHCR 公開前にコンテナをテストするには、対応する `containers/container-amd64.tar.gz` または `container-arm64.tar.gz` を読み込み、Compose を使用する前に `FLINTEYE_IMAGE=flinteye:release-amd64` または `flinteye:release-arm64` を設定してください。ダウンロードした Compose ファイルにある将来の GHCR タグを、すでに公開されているイメージと見間違えないように注意してください。

## 旧ビルドの自動検証結果

対象のアプリケーションコミットは `a0aa7592195a6b52cd732014603ea2fbc3ff4b22` です。[ビルド結果・検証用成果物](https://github.com/noguhiro2002/FlintEye/actions/runs/43800923694)を確認できます。Windows x64/ARM64、macOS Intel/Apple Silicon、Linux amd64/arm64の6構成すべてで、ビルドと自動動作確認が通りました。成果物はインストーラー8種（EXE、DMG、DEB、RPM）と、両CPU向けのコンテナアーカイブです。作成したアプリで、初回設定、認証、同梱メディア部品、テスト映像の録画・再生、通常の **Quit** 操作を確認しました。Windowsでは登録済みコマンドからのアンインストールとデータ保持、LinuxではDEB/RPMのインストールも確認しています。

Pythonテストは190件を実行し、失敗はありませんでした。環境に依存するため、ローカルで2件、Linux CIで3件をスキップしています。Chromiumでは画面テスト全18グループ、FirefoxとWebKitでは監視・初回設定・録画の操作を確認しました。LAN設定と初回設定は、3つのブラウザーエンジンすべてで画面幅320/1440ピクセルの追加確認を行っています。

独立したテスト環境でのLAN試験では、証明書の信頼、初回設定の本人確認、Secure属性のCookie、権限、テスト映像、再起動後の証明書・認証情報・録画の保持、通常のQuitを確認しました。Linux上のブラウザーエンジンやテスト映像による確認は、MacのSafari、モバイル端末、実カメラでの確認とは分けて扱います。

Actionsから取得した成果物は、GitHubが記録したサイズ・SHA-256と照合し、展開時にZIPのCRCも検証しました。同じコミットのリリース作成手順でまとめ、マニフェスト、全ファイルのチェックサム、コンテナのCPU・ソース情報、macOSのad-hoc署名の整合性を確認しています。Intel Macでは最初のDMG作成時にmacOSが `Resource busy` を返したため、同じコミットで再実行しました。他の対象で成功した成果物はそのまま使用しています。

この実行結果は改修前のコミットに対応します。今回の開発版の結果は、[公開前チェックリスト](RELEASE_CHECKLIST_1_2_0.ja.md)に沿って記録してください。
